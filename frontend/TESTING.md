**Testing & Mocking (Vitest + MSW)**

- **Purpose:** Describe how frontend tests and mock API behavior are set up and how to run them.

**Files of interest**
- `vitest.config.js` — Vitest configuration (jsdom env, setup file).
- `src/test/setup.js` — Vitest setup: starts/stops MSW test server and cleans up between tests.
- `src/test/server.js` — MSW Node server for tests (uses `setupServer`).
- `src/mocks/handlers.js` — Mock handlers for the API endpoints used in dev/tests.
- `src/mocks/browser.js` — MSW browser worker (dev) entrypoint.
- `public/mockServiceWorker.js` — Service worker file registered by the browser worker (generated by `npx msw init`).
- `src/main.jsx` — Starts MSW worker in development only (guarded by `import.meta.env.DEV`).

**How it works**
- During tests: Vitest loads `src/test/setup.js`, which starts a Node MSW server (`setupServer`) using `src/mocks/handlers.js`. Tests run against the mocked API responses.
- During development: `src/main.jsx` conditionally starts the browser MSW worker (from `src/mocks/browser.js`) when `import.meta.env.DEV` is true. The worker intercepts same-origin requests (relative URLs) and returns mocked data.
- Production: MSW is not started in production builds (no worker.start call in production), and the app uses the real backend URL.

**Run tests**
- Run all tests (watch):
```bash
cd frontend
npm test
```
- Run a single file:
```bash
npx vitest src/Form.test.jsx
```
- Run a single test by name:
```bash
npx vitest -t "calls onClick handler"
```
- Open the Vitest UI:
```bash
npm run test:ui
```

**Development with mocks (local app)**
- Ensure dev uses relative backend URLs so the worker can intercept. This repo sets `backendUrl` to `''` in DEV.
- Start dev server:
```bash
cd frontend
npm run dev
```
- Confirm worker registration in browser DevTools -> Application -> Service Workers. Network requests to `/api/...` should be `(from ServiceWorker)`.

**Notes about environment variables**
- `VITE_BACKEND_URL` is respected in production builds only. Do not keep a production backend URL in `frontend/.env` if you want dev to use mocks — move it to `.env.production` or set it at build time.
- To preview with mocks in a non-dev environment, you can add a Vite env flag and handle it in `main.jsx`, but be careful not to enable mocks in real production environments.

**Why `ctx` could be undefined (debug note)**
- MSW provides `ctx` helper functions to compose responses when using the library-provided `res` function. If a mismatched MSW bundle or wrong entrypoint is used (e.g., a Node-targeted build in the browser), handler arguments might differ and `ctx` can be undefined.
- This repo uses `import { setupWorker } from 'msw/browser'` to ensure the browser worker implementation is used. If you still see `ctx` undefined, double-check `public/mockServiceWorker.js` is present (generated via `npx msw init public/`) and that `src/mocks/browser.js` imports from `msw/browser`.

**Troubleshooting**
- Blank page in dev: check console for `worker.start()` errors. Wrapping `worker.start()` in try/catch prevents worker failures from blocking rendering.
- Requests still hitting real backend (CORS errors): ensure dev uses relative URLs (''), and remove or move `VITE_BACKEND_URL` out of `.env` used by dev.
- Worker not registered: run `npx msw init public/ --save` to copy the correct `mockServiceWorker.js` into `public/`.

**Pro Tips**
- Keep component tests (unit) and integration tests separated. Use MSW for integration/user-flow tests that involve network requests.
- Use `server.resetHandlers()` in tests to change responses per-test.
- If you prefer MSW's `ctx` helpers, handlers can return `res(ctx.status(...), ctx.json(...))`; ensure `msw/browser` is used and the worker file matches the MSW version.
